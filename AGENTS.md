# Проектные правила

## Цель проекта

Создать профессиональную киберспортивную платформу eFootball Nexon для турниров, матчей, рейтингов, достижений, дивизионов, уведомлений и админского управления.

## Стиль проекта

- современный
- премиальный
- минималистичный
- взрослый
- спортивный
- киберспортивный
- без детского дизайна
- без кислотных цветов
- без визуального мусора

## UI требования

- Идеальная адаптация под мобильные устройства, планшеты, ПК и 4K.
- Каждая новая страница корректно отображается от 320px до 4K.
- Запрещены горизонтальный скролл, переполнения, наложения и прыжки интерфейса.
- Использовать матовый черный фон, мягкую белую типографику, металлические золотые акценты.
- Дизайн должен выглядеть как профессиональная футбольная esports-платформа, а не мобильная игра.
- Кнопки, формы, карточки, таблицы и модальные окна должны быть компактными и читаемыми на телефонах.
- Новые UI-блоки обязаны повторно использовать существующие компоненты и CSS-паттерны проекта.

## UX требования

- Минимум кликов для основных действий.
- Понятная навигация без скрытых критичных действий.
- Логичное расположение элементов: важное выше, вторичное ниже.
- Высокая скорость работы на крупных турнирах.
- Любое действие администратора должно иметь понятное состояние: загрузка, успех, ошибка.
- Ошибки должны объяснять, что именно нужно исправить.

## Код требования

- TypeScript strict.
- Запрещен `any`; использовать точные типы, `unknown` с сужением или типы Prisma.
- Запрещено дублирование бизнес-логики между API, страницами и компонентами.
- Запрещено создавать технический долг ради быстрого визуального результата.
- Использовать существующую архитектуру, enum Prisma, Zod-схемы, сервисы и дизайн-систему.
- Не менять несвязанные файлы.
- Не удалять историю матчей и статистику без явного требования.
- Не смешивать UI-логику, пересчет таблиц и мутации базы в одном новом месте.

## Перед изменением

1. Найти связанные файлы через `rg`.
2. Понять модель данных Prisma и существующие enum.
3. Найти API, UI-компоненты, серверные сервисы и страницы, связанные с задачей.
4. Объяснить причину проблемы.
5. Построить короткий план.
6. Только после этого менять код.

## Перед завершением задачи

Проверять:

- build
- lint
- TypeScript
- runtime ошибки
- импорты
- адаптивность
- производительность
- безопасность

Если проверка не запущена, явно указать причину.

## Турнирная система

Перед любыми изменениями проверять:

- групповой этап
- плей-офф
- серии Best Of
- пенальти
- пересчет таблиц
- удаление матчей
- редактирование матчей
- замену участников
- статистику игроков
- статистику команд
- регистрацию одиночных, кооперативных и командных составов
- исторический состав кооп-матча через `MatchLineupPlayer`
- уведомления Telegram
- ограничения тестовых турниров

Правила рейтинга и статистики кооп-матчей:

- После подтверждения счета обязательно сохранять снимок состава матча через `ensureMatchLineupSnapshot`.
- Рейтинг и статистика сыгранного кооп-матча должны считаться по `MatchLineupPlayer`, а не по текущему `TournamentRegistration.rosterMembers`.
- Замена игрока после сыгранного матча не должна переносить старые рейтинг/статистику на нового игрока.
- Новые матчи после замены должны получать новый снимок состава и считаться новым игрокам.

## База данных

- Все изменения схемы делать через Prisma migration.
- Перед изменением связей проверить cascade/onDelete.
- Для тяжелых списков использовать индексы, выборочные `select`, пагинацию или поиск.
- Не загружать все матчи/участников, если UI показывает только найденные или отфильтрованные данные.
- `MatchLineupPlayer` является историей состава конкретного матча; не удалять и не пересоздавать ее без явного миграционного плана.

## Админ-панель

- Опасные действия должны быть подтверждаемыми.
- Практикант не может открывать и менять реальные турниры.
- Тестовые турниры не видны игрокам и не отправляют массовые уведомления.
- В списках участников и матчей поиск должен работать по имени, email, Telegram, клубу и команде, если эти поля доступны.

## Качество

- Изменение считается готовым только если оно не ломает существующие турниры.
- Любая логика матча должна одинаково работать в публичной странице, админке и API.
- Любая новая функция должна иметь понятные состояния для мобильных устройств.
- Документация агентов находится в `.agents/`.
